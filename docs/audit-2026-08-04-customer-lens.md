## 三、明确不做（产品边界文档）

| 不做 | 理由 |
|---|---|
| **M34 批次层 / 批号台账 / 效期管理 / FIFO** | **这等于放弃药店行业，我接受这个代价，并且要写进定位。** 理由：①药监飞检、GSP 台账是合规刚需，药店愿意为它付费给专业软件，我们打不过也不该打；②Batch 表会污染 Inventory / 盘点 / 开单 / 报表全链路，每一条 P0 的修复成本都要乘一遍；③1800 SKU 的店本身就不是「30 秒配成自己行业」的目标客群。**替代方案（P2）**：商品级单值「最近到期日」+ 到期提醒，只解决食品/母婴/化妆品的「这个货快过期了」，明确不解决「这一批」。不要拿它冒充批次管理。 |
| **多仓库 / 调拨** | 背书 PM 判断。schema 里连 Warehouse 概念都没有，加进来污染全链路。「店里+家里」用盘点单+备注扛。3 家以上真实用户主动提再说。 |
| **资产负债表 / 现金流量表** | 个体户看三件事：今天赚多少、谁欠我钱、还有多少货，三张我们都有。做了是给自己贴「专业软件」标签，砸掉零学习成本话术。 |
| **会员储值 / 积分** | 收银 POS 的地盘。我们不接收款码、不管排队，做半截只会让用户在两个系统里各存一份客户。 |
| **满减 / 买赠 / 促销规则引擎** | 整单折扣 + 客户专属价 + 单品改价（M9 修完）覆盖批发议价 90%。规则引擎配置成本高于收益，且和「AI 口述记账」的极简心智直接冲突。 |
| **自建商品条码库** | 降 P2 且不自建。条码库只对标品有意义（服装/餐饮/自制品/散装货根本没条码），自建是无底洞。冷启动主武器继续是 AI 批量建品 + 粘贴导入 + 一键搬家——那是竞品做不好的，条码库是他们的强项，追平即可。 |
| **完整离线优先（本地库 + 双向同步 + 冲突解决）** | 成本极高，且 Web 端上线后两端同步复杂度指数级上升。降级为只读缓存 + 不丢购物车 + **改话术**（见 M36）。 |
| **多级 BOM / 工序 / 损耗率** | M35 只做一级 Recipe(ownerSku → componentSku, qty)，覆盖奶茶/烘焙/小吃/早餐/卤味。多级 BOM 是 ERP，做了会拖垮迭代还打不过专业软件。 |
| **独立「应收看板」页面** | 功能要做，页面不新增。全部并进客户详情页 + 客户列表排序。守「功能多一个，老板娘就多懵一分」。 |

## 五、如果只能做三件事

### 1. 让钱能记回来 —— M2 收欠款（销售单 + 客户维度）+ M16 口述默认挂账

**为什么第一**：这不是缺功能，是**核心留客报表持续输出错数字**。三个视角独立撞上同一个洞：接口写好了、进货侧对照组也做对了、唯独客户侧断掉。而它污染的是我们最想守的资产——客户对账单、欠款预警、AI 问生意的「谁欠我钱」。更狠的是口述那条路：老板赊出去的货被记成「已收」，账上永远查不出来。**修复成本几乎为零（后端全现成），伤害是每天累积且不可逆的。**

### 2. 让第一单开得出来 —— M13 中间按钮 + M3 散客 + M7 负库存

**为什么第二**：这三条是同一个失败瞬间的三个切面——新用户装上 App 的头 5 分钟。中间那个最大最亮的按钮把他引到「改库存不记钱」的死路；就算他找对了开单，「请先选客户」把他挡在门外；就算他建了客户，「库存不足」又把单打回。**任何一条单独出现都是卸载理由，三条叠在一起是必然卸载。** 而三条的修复加起来不到半天，全部是小改动（其中中间按钮那条只是 tab 顺序，因为「开单」tab 本来就存在）。留存是所有后续价值的乘数。

### 3. 让账能信 —— M1 成本可信度三件套（快照 + 不许 AI 编 + 缺失标注）

**为什么第三**：五个视角同时提到，全场权重最高。首页那个 40 号字的「今日毛利」是这个产品的主视觉、也是老板每天唯一会看的数字，而它现在由三个洞共同喂养：AI 按售价 60-75% 编出来的假成本、快速建品压根不问的空成本、以及会被下个月进价追溯改写的历史成本。**错得「很像真的」是最坏的一种错**——成本是 0 老板一眼看穿，4.2 他只会觉得「今年生意一般」，然后照着这个数去多进货。

### 为什么不是 AI 差异化（M33 微信订货 / M32 拍照进货）

它们才是定位的上限，我知道。但**AI 提高的是数据写入速度，写入速度 × 错误率 = 灾难**。在成本会被编、赊销会被记成已收、收款没地方记、库存会静默取整的地基上，让老板用一句话每天写进去 20 条记录，只是让账更快地错到无法收拾。这三件做完，M33（改一个 mode 参数、不用新模型）立刻升为下一个 P0——那时候 AI 写进去的每一条才是对的，「30 秒配成自己行业」才不是一句会反噬的宣传语。

### [major] 月底给 40 个客户发对账单只能一个一个点进去分享，而且没有「上月」这个日期预设

## 产品经理（竞品对标视角）。审查方式：先读 competitor-analysis-2026.md / zhihuiji-teardown-2026.md / scaling-and-web-design.md 定基线，再逐条去代码里验证"文档说有的到底有没有、竞品标配我们缺哪些"，只报有文件:行号证据的。已知两个 P0（假必填、商品 pageSize）不再重复；scaling 文档里已写的（图片、分组字段、分页、多租户、权限点、Web端）也不重复。

【产品边界 · 明确不做，理由写进定位】
1. 多仓库 / 调拨：teardown 已定不做，我同意。补充理由——我们连"仓"这个概念都没有（schema 无 Warehouse），加进来会污染 Inventory/盘点/报表全链路。真实小老板的"店里+家里"两处货，用"盘点单+备注"能扛过去。等有 3 家以上真实用户主动提再说。
2. 资产负债表 / 现金流量表：不做。个体户不看会计报表，看的是"今天赚多少、谁欠我钱、还有多少货"，这三张我们都有（经营利润/对账单/库存统计）。做了是给自己贴"专业软件"标签，反而砸掉"零学习成本"的话术。
3. 先进先出 / 批次成本 / 效期管理：不做。那是药品 GSP、生鲜批发的重装备，我们只做"移动加权 + 单据成本快照"（见发现 #2），能覆盖 95% 场景且用户无感知。
4. 会员储值 / 积分：不做。这是收银 POS（客如云/美团）的地盘，不是进销存的。我们没有收银场景（不接收款码、不管排队），做半截的会员只会让用户在两个系统里各存一份客户。
5. 满减 / 买赠 / 阶梯促销规则引擎：不做。我们已有整单折扣 + 客户专属价 + 单品改价（#5 修好之后），覆盖批发议价 90% 的需求。促销规则引擎是零售连锁的东西，配置成本高于收益，且和"AI 口述记账"的极简心智直接冲突。
6. 商品条码库（外部 EAN 数据库）：降级为 P2，不自建（见发现 #7）。先把"扫不到就地建档"补上，条码库以后接第三方 API，且只对标品行业有价值。

【建议补的优先级】#1 收欠款 → #3 允许负库存 → #2 成本快照+移动加权 → #5 开单行改价改量 → #4 小数数量 → #6 客户详情页 → #7 扫码建档 → #8 离线口径改写。前四条都是"每天都会撞上"，其中 #1 #2 会让账越记越错。

(a) 单位:档案里红牛单位是「罐」。老板说「进了2箱红牛,120块」,AI 返回 quantity=2 / unit=箱 / matchedProductId=红牛。确认卡显示「红牛 2箱 · 共¥120 [已有商品]」,老板一看没错,确认。库存 +2 罐(真实进了48罐)。下次开单系统说没货,老板对着满仓的红牛发火。
(b) 金额:老板说「卖了7袋馄饨,收了100」。AI 同时填 totalAmount=100 和 unitPrice=14.29。确认页显示 ¥100(前端取总价),落库的订单是 7×14.29=¥100.03,收款流水也是 100.03。抹零、整数收钱在摊位/农贸是天天发生的事,月底客户对账单永远差几分几毛,老板查不出为什么。
(c) 小数:老板说「进了3.5斤面粉」→ Math.round → 库存 +4 斤。散装/生鲜生意每天都在丢货。
- **证据**：(a) aiParse.js:244 `const qty = Math.round(item.quantity)` 与 322 直接加减库存,全程不比对 matchedProduct.unit;matched 分支下 unit 只用于展示(voice_entry_screen.dart:458/494 显示的是**说出来的**单位,不是商品档案单位)。(b) 前端 core/models.dart:418-419 `effectiveAmount => totalAmount ?? (unitPrice ?? suggestedPrice) * quantity`(总价优先) vs 后端 aiParse.js:288 `let unitPrice = s.unitPrice ?? (s.totalAmount/qty)`(**单价优先**)——两边优先级正好相反。而这个单价是提示词 aiParse.js:33 明确要求 LLM 自己算的「unitPrice(单价,2位小数)」。(c) prisma/schema.prisma:144 `quantity Int @default(0)` + aiParse.js:244/284 Math.round。
- **建议**：① **LLM 不做算术**——这是典型的该用规则却塞给 AI。提示词只让它抽原文出现过的数字(quantity、totalAmount),删掉 unitCost/unitPrice 两个要求 AI 做除法的字段,单价一律后端 total/qty 算一次,前后端用同一份计算结果。② 单位加一层确定性拦截:matched 且 AI 给的 unit ≠ 商品档案 unit → 确认卡红字「你说的是『箱』,红牛的单位是『罐』」,并弹「1箱 = __罐」让老板填一次(存下来下次自动换算)。AI 只负责把这句话问出来,换算本身是纯规则。③ 小数量:要么 Inventory.quantity 转 Decimal,要么在确认卡上明说「按整数记,3.5→4」而不是偷偷 round。

### [blocker] AI 配错商品后无法改绑——点「编辑」改名字是假的,老板以为修好了其实没变

- **场景**：档案里同时有「茅台镇原浆酒」和「飞天茅台53度」。老板说「今天卖了两瓶茅台」。AI 拿不准填了 null,后端兜底用无排序的字符串包含,静默命中了先建的那个「茅台镇原浆酒」。确认卡显示的商品名是老板说的「茅台」,只在旁边一个小标签写「扣库存」——老板根本看不出配错了。就算他从库存数字看出不对,点铅笔图标进编辑,把名字改成「飞天茅台53度」,点确定——界面上名字变了,他放心确认入账。结果:后端拿的还是旧的 skuId,扣的还是原浆的库存,开单价格用的还是原浆的价,单据上打印出来的商品名是从 skuId 反查的原浆。老板做了一次修复动作,系统一个字都没听。这比「不给改」更恶劣,因为它让人相信改成功了。
- **证据**：voice_entry_screen.dart:556-580 `_editPurchase`/`_editSale` 的 setState 只赋值 name/quantity/unit/totalCost(totalAmount),**从不触碰 matchedProductId / skuId**;提交时 voice_entry_screen.dart:184-195 仍然发旧 skuId。后端 aiParse.js:282 按 skuId 取 sku,310-311 用 `r.sku.product.name` 落 OrderItem——前端改的 name 被完全丢弃。UI 上卖出条目只有「换规格」(_pickSku,271-294)没有「换商品」,进货条目只有「选品类」(_pickType)。兜底匹配 aiParse.js:64 `findFirst({ where:{ isDeleted:0, name:{contains:clean} } })` 无 orderBy 无候选提示,静默取一条。附带:aiParse.js:83-84 把全量商品和客户塞进提示词、无 take,几百个商品之后匹配质量和延迟一起掉。
- **建议**：① 每个条目加「换商品」入口,把 Top3 相似商品(带规格/售价/库存)列出来让老板点一下——这是 AI 最该干的活:出候选,不是替人拍板。② 兜底命中 ≥2 个候选时**绝不静默选第一个**,标成待确认态「有3个相似商品,点一下确认是哪个」,未确认不允许入账。AI 都认怂填 null 了,规则却在瞎猜,这是反过来的。③ 编辑弹窗里改了名字就必须重新走一次匹配(或直接把「改名」改成「换商品」)。④ 商品上千后改成先用关键词粗筛出 50 个候选再喂提示词,别全量灌。

### [blocker] AI 生成商品时编造成本价、确认页还看不见,毛利报表长期错得「很像真的」

- **场景**：新用户上手最爽的一步:建好品类点「AI 生成商品」,8 个常见商品秒出。确认弹窗里每行显示「红牛 ¥6」,老板扫一眼觉得价差不多,全选创建。他不知道每个 SKU 后面还静静躺着一个 AI 按「售价的60-75%」编出来的成本价 ¥4.2(他实际进价 3.1)。之后每一张经营利润表、每一次员工业绩毛利、AI 问生意回答的「这个月赚了多少」,全部基于这个编的数。要命的是错得很像真的——如果成本是 0,老板一眼能看出毛利虚高;4.2 这个数只是让他觉得「今年生意一般」,他永远不会去查。粘贴导入(/ai/import-products)同一条链路,同样问题。
- **证据**：server/src/controllers/ai.js:28 提示词原文 `costPrice(建议成本价，约为售价 60-75%)`——明确指示 LLM 编。前端草案确认单 app/lib/features/types/type_edit_screen.dart:480-484 的 subtitle 只渲染 `specValues + ¥price + 库存`,**costPrice 全程不出现在任何一个界面上**。落库走 products.js:199 `createProductCore(..., { strict:false })`,costPrice 原样写进 Sku(skuInputSchema products.js:9)。消费端 reports.js:51 `cogs = quantity * (sku.costPrice ?? product.costPrice ?? 0)`,ai.js:129 的 AI 问生意快照同样用它。
- **建议**：① **AI 不许编成本价和售价**,提示词里 costPrice 直接删掉,price 也标成「参考值」。成本价是钱,不是常识题。② 草案确认单必须把成本列出来,空的显示灰字「首次进货时自动填」——用户看见空的才会去填。③ 真正该用 AI 的位置在后面:第一次进货(不管走进货单还是口述)时把实际进价回写成 SKU 成本,并在毛利报表顶部标出「有 N 个商品还没有真实进价,毛利未计入」。这一步比开局编一个数有用一百倍,而且是确定性逻辑,不需要 AI。

### [major] 账单截图 OCR / 汇总营业额与销售单重复计收入,零去重零提示

- **场景**：这个功能的宣传语就是「🧾 传收款账单截图(微信/支付宝日账单)」。摊主白天用口述记账记了 8 笔卖出(生成了 8 张订单共 ¥960),晚上收摊顺手把微信收款助手的「今日收款 ¥1280 共32笔」截图传进来——那 32 笔里本来就包含白天那 8 笔。系统建一条 ¥1280 的 Income,确认卡只写「计入收入,不涉及库存」。当天营业额变成 ¥2240,毛利虚高一倍多,月度利润表、AI 问生意的「这个月赚了多少」全部跟着错。老板要么信了(高兴地扩大进货),要么发现对不上后彻底不再信这个 App 的报表——后者更致命。
- **证据**：aiParse.js:365-377 aggregates 无条件 `tx.income.create`,不查当日已有订单/收入。消费端 reports.js:50 `sales = 订单 actualAmount 之和 + incomes 之和`,reports.js:42 按日走势同样把 income 直接 bump 进 sales;AI 问生意快照 ai.js:128 一模一样地相加。提示词 aiParse.js:36 只教 AI「优先取今日合计,不要拆成单条」,完全没有与已记数据比对的概念。前端 voice_entry_screen.dart:510-525 汇总条目只显示金额和一句「计入收入,不涉及库存」。
- **建议**：① 解析时把「该日期已有订单合计 / 已有收入合计」一起返回,确认卡上把汇总条目和它并排显示:「今天已记 8 单共 ¥960,这笔 ¥1280 是含在里面吗?」给三个选项:全是新的 / 已包含(只补差额 ¥320) / 删掉。② 这恰恰是 AI 真正能干的判断——32 笔 vs 8 单、金额包含关系,规则写不利索,LLM 一眼就懂。把当日明细喂进提示词让它直接给冲抵建议。③ Income 落库时记一个 source='bill_ocr' + 日期,同一天重复传第二张截图时直接提示覆盖而不是叠加。

### [major] 「AI 问生意」是单轮的却长着聊天脸;快照只有「本月」,时间对比/趋势/预测全废,「哪些货要补了」还会自信答错

- **场景**：老板打开 AI 问生意,界面是气泡对话框加历史消息,他自然按聊天习惯来:问「这个月赚了多少?」——答得挺好。追问「那上个月呢?」——快照里根本没有上月数据,AI 只能说「这个我手头数据答不了」。再追问「他欠了多久了?」——AI 连「他」是谁都不知道,因为每次请求只带这一句话,前面的对话从没上传过。三个来回后老板得出结论:这玩意儿只能答那五个预设按钮。更糟的是预设按钮里那句「哪些货要补了?」——补货判断依赖每个 SKU 手工设的最低库存,默认值是 0,绝大多数用户从没设过,所以快照里的「预警缺货」永远是空数组,AI 会用非常肯定的口吻回答「目前没有需要补货的商品」。老板信了,周末断货。这是整个 App 里最危险的一句 AI 回答。
- **证据**：单轮:app/lib/features/reports/ask_screen.dart:38 每次只发 `{'question': question}`,本地 _msgs 从不上传;server/src/controllers/ai.js:152-155 每次重建快照 + 单条 user message,无 history 参数。快照维度:ai.js:63-147 buildBusinessSnapshot 只有「本月」一个区间 + 今日订单数,没有上月/同期/按日趋势/单品动销速度。补货:ai.js:123 `if (inv.minQuantity > 0 && inv.quantity <= inv.minQuantity)`,而 minQuantity 默认 0(products.js:11 `.default(0)`、aiParse.js:231 口述建品写死 `minQuantity: 0`);同一套判据也是首页「该补货了」卡(dashboard_screen.dart:211)、inventory.js:126、stats.js:17 的唯一依据。预设问题在 ask_screen.dart:20。
- **建议**：① 带上最近 5 轮对话历史(前端已经有 _msgs,顺手的事),否则就把界面改成搜索框别做成聊天——聊天 UI 承诺了多轮,做不到就是欺骗。② 快照扩维:本月/上月/上上月三段 + 近30天按日 + **每个 SKU 近30天日均销量与「按当前库存还能卖 N 天」**。第三项是关键——有了它,「茅台还能卖几天」「哪些货要补了」「哪个货压死了资金」才答得了,这也是竞品拆解文档自己写下的差异化目标。③ 补货判断从 minQuantity 换成「日均销量 × 补货周期」的确定性公式(这一步不该用 AI,公式比 LLM 稳),AI 只负责把结论说成人话并直接生成进货单草案。④ 在快照答不了时不要只说「答不了」,把「你可以问我这些」列出来。

### [major] 新机会:送货单/进货清单拍照 → 进货单草案(现在完全不存在,且当前模型栈根本吃不了图)

- **场景**：老板从批发市场拉货回来,手里一张 20 行的手写或热敏打印送货单。**没有 AI 的现状**:打开新建进货单,一行行搜商品、填数量、填进价、核对总额——20 行至少 15-25 分钟,而且这活儿只能晚上收摊后干,人最累的时候最容易录错数字;很多老板干脆放弃,单子往抽屉里一塞,库存和应付账款从此对不上。**有 AI 之后**:拍一张照,5 秒出 20 行草案(商品已匹配档案、进价已带出、总额已核对),老板扫一眼改两处,1 分钟入账。一次省 15-25 分钟,进货频次一周 2-3 次的店铺,一个月省 2 小时以上。这也是唯一一个能让老板「拿到货的第一时间就把账记完」的路径——记账拖到晚上就是记不准的根本原因。
- **证据**：现有图片能力只有 app/ios/Runner/AppDelegate.swift:31-44 的 iOS Vision `VNRecognizeTextRequest`,输出是扁平的文字行数组(`lines.joined(separator:"\n")`),没有版面/表格/列对齐信息;它唯一的下游是口述记账(voice_entry_screen.dart:125-131,还硬加了「账单截图内容：」前缀),而 aiParse.js:36 的提示词只认「微信收款助手/支付宝账单」。模型是 server/.env `DEEPSEEK_MODEL="deepseek-chat"`,纯文本,deepseek.js:16-19 的 messages 也只拼字符串——**当前 AI 栈物理上不支持读图**。
- **建议**：① 这是当前 AI 能力栈的硬缺口,必须引入一个多模态模型(Qwen-VL / GLM-4V / doubao-vision 一类,按图计费,量不大)。iOS Vision 留着做印刷体快路径 + 离线兜底,手写单和表格版面必须走 VL。② 产品形态直接复用已经打磨好的「三态确认流」:每行标 已匹配商品 / 新商品待归类 / 没看清请手填,和口述记账长一个样,零学习成本。③ 顺手把供应商、单据日期、总额一起抽出来,直接生成完整进货单(带应付款),而不是像现在的口述进货那样只加库存不记钱——顺便补上「口述进货不生成 PurchaseOrder、不写付款流水,资金流水报表看不见这笔支出」这个洞(aiParse.js:207-265 全程无 PaymentRecord,对比 purchaseOrders.js:99)。④ 拍照转单据是唯一能同时打「智慧记手写单拍照」和「秦丝学习曲线陡」两个点的功能,优先级应该高于任何界面优化。

### [major] 新机会:客户微信订货消息 → 销售单草案(竞品已有;我们的提示词铁律会把它直接判死)

- **场景**：送货型批发老板每天早上的固定动作:微信里翻 7-8 个客户的消息——「明天来两件飞天,一件普五」「老规矩,加两箱」「上次那个价再给我三提」——记在本子上,回店里再一单单开出来。**没有 AI 的现状**:翻+抄+开单每天 20-30 分钟,漏单、记错量、记错客户是家常便饭,漏一单就是一次客户投诉。**有 AI 之后**:截图或长按复制粘贴进来,3 秒出草案——客户已认出(客户语义匹配已经做好了)、商品已匹配、价格已经走完专属价>上次成交价>标价三级、送货日期和备注一起抽出来,老板核对后一键生成销售单。每天省 20-30 分钟。更关键的是:这是能把「AI 原生」讲成故事的一步——老板早上什么都不用干,打开 App 今天要送的货已经列好了。而现在把这段微信文字喂进去,得到的是零条目 + 一句「没听清是进货还是卖出」。
- **证据**：aiParse.js:37-39【方向判定铁律】:「只有出现明确进货动词(进了/买了/补了/采购/拿货)才归 purchases;明确卖出动词(卖了/出了/走了/某客户拿了)才归 sales」+「只报了商品和数量、没有方向动词 → 一律不归类,放 warnings」。客户订货语是典型的无方向动词句式(「来两件」「加两箱」「给我三提」),100% 命中这条铁律被丢进 warnings。OCR 链路 voice_entry_screen.dart:130 还会强行加「账单截图内容：」前缀,进一步把模型往收款账单上带。竞品调研已明确记录智慧记有「微信聊天记录识别」(docs/competitor-analysis-2026.md:12)。
- **建议**：① 不需要新模型,只需要**新的意图入口**:解析请求加一个 mode 参数(freeTalk 老板自述 / customerOrder 客户订货)。customerOrder 模式下把方向铁律替换成「默认全部是卖出」,并额外抽取 送货日期、地址、备注。入口就放在口述记账页现有的两个圆按钮旁边加第三个「📋 客户订货」,或者做成 iOS 分享扩展——在微信里长按消息选「分享到智存」是最短路径。② 复用已有的客户语义匹配和三级价格解析,这两块代码一行都不用改(aiParse.js:118-151)。③ 配合上一条的赊销修复:客户订货默认落「挂账」,天然正确。④ 多客户混在一条消息里时,已有的「按客户分单」逻辑(aiParse.js:274-276)直接就能用——这是我们比竞品更完整的地方,值得当卖点。
