# 商品体量 · 字段自定义 · Web 端与权限 —— 汇总设计（2026-08-04）

回答四个问题：①商品要不要显示图片 ②商品多了怎么找 ③必填字段能否用户自定义 ④Web 端与统一账户赋权怎么设计。

## ① 商品图片：显示，但要有降级和密度切换

**结论：显示，且必须有无图降级。**

不同生意对图片的依赖差别极大：
- 药品/馄饨/酒水：名字+规格就能唯一识别，图片是锦上添花
- 服装/玩具/饰品/烘焙：图片就是主要识别方式，没图等于没法选

所以不能一刀切，方案是：

**a) 列表统一显示缩略图，无图不留破框**
- 有图 → 52×52 圆角缩略图
- 无图 → 显示品类图标或商品名首字色块（跟头像同款处理），绝不显示灰色破图占位
- 覆盖范围补齐：商品库存页（已有）、**品类详情页的商品列表（缺）**、**开单选货弹窗（缺）**、**进货选货弹窗（缺）**
- 开单选货最该有图——选货是最需要视觉确认的一步

**b) 列表密度切换（存 Setting，全局生效）**
- `列表模式`：紧凑单行，一屏 8-10 个，适合批发/药店这种靠名字识别的
- `大图模式`：两列卡片带大图，适合服装/饰品/烘焙
- 跟主营品类一样，设一次全局生效，不用每页切

**c) 性能**
- 缩略图走服务端裁剪（`/uploads/xxx?w=120`）或上传时生成缩略图，别在列表里拉原图
- 列表滚动用 `cacheExtent` 限制，避免一次性解码几百张图

## ② 商品多了怎么找：不做树形分类，做「可分组字段」

**结论：不新建二级分类表，把已有的自定义字段升级成分组维度。**

### 为什么不做树形分类

直觉方案是"品类 → 二级分类 → 商品"，加一张 Category 表。但这套在通用引擎里是错的：

- 药店想按"感冒药/消炎药/外用药"分，服装店想按"春夏/秋冬"分，酒水店想按"香型"分——**每个行业的分组维度都不一样**，做成固定的一层树，等于逼所有人用同一个抽象
- 而且**这些维度已经在 FieldDefinition 里了**：酒水品类现在就有"子类"字段，药品品类也有

### 方案：字段加一个「用作分组」开关

`FieldDefinition` 加一列 `groupable`（或复用现有 `isCore` 语义外的新字段）：

```prisma
model FieldDefinition {
  // ... 现有字段
  groupable Int @default(0)  // 1 = 商品列表可按它分组/筛选（仅 type=select 有意义）
}
```

用户在「字段设置」里给某个 select 字段打开「用作分组」，商品列表顶部就多一行该字段的筛选 chips：

```
商品库存
[搜索框]
[全部] [馄饨★] [药品] ...        ← 品类（已有）
[全部] [感冒药] [消炎药] [外用药]  ← 分组字段（新，按"子类"）
```

**这套的好处**：
- 零新表，零新概念，用户已经理解"字段"了
- 需要两级？开两个字段（大类+小类）当分组即可，比固定两层树更灵活
- AI 生成字段时可以顺手标记哪个适合做分组（提示词里加一条）
- 不需要分组的行业完全无感知，界面上不会多任何东西

### 搜索

商品库存页已有（匹配 名称/编码/条码/规格）。要补的：
- **品类详情页的商品列表**（现在没有）
- 搜索支持拼音首字母（如 `gml` → 感冒灵）——商品上千时这个提效最明显，需引入拼音库

### 排序

商品列表加排序入口，默认值很重要：

| 排序 | 场景 |
|---|---|
| **最近有动静**（默认） | 常进常卖的浮到最上面，最贴合日常开单 |
| 库存少→多 | 补货前扫一眼 |
| 名称 | 找特定商品 |
| 销量高→低 | 看什么好卖 |
| 售价 | 比价 |

默认选「最近有动静」而不是"创建时间倒序"——开单时想找的永远是常卖的那几个。

### 分页

后端 `/products` 已支持 `page`/`pageSize`，App 端改成滚到底自动加载下一页（`ListView` + `ScrollController` 触底加载）。搜索/筛选走服务端，别在客户端 filter 全量数据。

## ③ 必填字段自定义：开关已有，缺的是真校验

**现状**：`FieldDefinition.required` 后端已有且**服务端确实在校验**（`products.js:35` 的 `validateFields`，建品/改品/建规格/改规格四处都调了，curl 实测返回 400 + 逐字段错误）。字段设置页有「必填」Switch（`type_edit_screen.dart:342`），表单渲染 `*`（`product_form_screen.dart:593`）。缺的只是 App 端前置检查。

### 要补的

**a) 前端前置校验（已完成）**
保存前列出所有缺项，不用等服务端来回：
```
还差 3 项必填：品牌、生产厂家、批准文号
第 2 个规格还差：规格
```

**b) 字段可编辑范围划清楚**

| 字段 | 能改标签 | 能改类型 | 能改必填 | 能删 |
|---|---|---|---|---|
| 系统核心（商品名/售价/库存/品类） | ✗ | ✗ | ✗（永远必填） | ✗ |
| AI 生成/用户自建的字段 | ✓ | ✓ | ✓ | ✓ |

系统核心字段不能动——没有名字和价格的商品在进销存里没有意义。其余全部交给用户。

**c) 删字段的数据处理**
自定义字段值存在 `Product.customFields`（JSON 字符串）。删字段时不物理清洗历史数据，只从定义里移除（旧数据里的键留着但不再显示）。理由：用户可能删错，留着能恢复；而且清洗大表有风险。**要在删除确认框里说清楚**："删除后新商品不再显示这个字段，已有商品的旧值会保留但不显示。"

**d) 字段排序**
字段设置页支持拖拽排序（`sortOrder` 已有），决定商品表单里的字段顺序——常填的往上放。

## ④ Web 端 + 统一账户赋权

### 前置：多租户隔离（不做这个，Web 端不能上线）

**现状最大的坑**：所有注册账号共享同一份数据。现在两个人注册，能互相看到对方的商品、订单、客户。App 阶段因为只有你自己在用没暴露，**Web 端一上线就是数据事故**。

必须先做：

```prisma
model Shop {
  id        Int      @id @default(autoincrement())
  name      String
  ownerId   Int
  createdAt DateTime @default(now())
}
```

- 所有业务表加 `shopId`（Product / Sku / Inventory / Order / PurchaseOrder / Customer / Supplier / Income / Expense / PaymentRecord / InventoryRecord / Stocktake / ProductType / FieldDefinition / PricingRule）
- User 加 `shopId`（一个用户属于一家店；未来支持多店再加中间表）
- **在 Prisma 中间件层强制注入 shopId**，而不是每个 controller 手写 where——手写必漏，漏一个就是越权
- 注册时自动建店并成为 owner；老板建员工时继承 shopId
- 迁移：现有数据全部归到 shop=1

这是所有后续的地基，也是 AI 计费（按店计量）的前提。

### 权限模型：从硬编码 role 升级到权限点

**现状**：`role: admin | staff` + `adminOnly` 中间件硬编码。App 阶段够用，Web 端不够——Web 上会出现"财务只看报表不能改库存""仓管只管出入库不看利润"这类需求。

**升级为「角色 → 权限点」**：

```
Permission（代码常量，不入库）
  product.view / product.edit / product.delete
  order.create / order.return / order.cancel
  purchase.create / purchase.pay
  inventory.adjust / inventory.stocktake
  report.sales.view / report.profit.view / report.cashflow.view
  customer.manage / supplier.manage
  staff.manage / settings.manage / data.export
  ai.use

Role（可预设+自定义，入库）
  老板   = 全部
  店长   = 除 staff.manage/settings.manage/data.export 外全部
  销售   = product.view, order.*, customer.manage, report.sales.view
  仓管   = product.view/edit, inventory.*, purchase.*, 不含任何 report.profit/cashflow
  财务   = 全部 report.*, data.export, 不能改业务数据
```

改造点：
- 后端中间件 `adminOnly` → `requirePermission('report.profit.view')`，一处定义两端共用
- `/auth/profile` 返回当前用户的权限点数组，前端据此隐藏入口（App 和 Web 同一套逻辑）
- **前端隐藏只是体验，后端拦截才是安全**——现在已经是这个原则，继续保持

好处：Web 端加一个角色，App 端立即生效，不用两边各写一套。

### Web 端定位：不是 App 的复制品

App 和 Web 该做各自擅长的事，重复建设是浪费：

| | App 擅长 | Web 擅长 |
|---|---|---|
| 输入 | 扫码、拍照识别、语音口述、随手记 | 键盘批量录入、Excel 粘贴导入、表格里直接改 |
| 场景 | 摊位上、仓库里、进货路上 | 办公桌前、月底对账、盘点汇总 |
| 输出 | 单据图片分享、蓝牙小票 | 大屏报表、批量打印、导出 |

**Web 端优先做这四块**（App 上做不好的）：
1. **批量商品管理**：表格式编辑，改价改库存像 Excel 一样拖拽填充
2. **大屏报表**：多维度交叉分析、图表、对比区间
3. **批量单据**：一次开多张单、批量打印
4. **员工与权限管理**：角色配置这种低频重操作，在大屏上做才顺手

**技术选型**：Vue3 + Element Plus（你已有 cool-admin-vue 可复用脚手架）。后端零改动——现在的 REST + JWT 天然支持多客户端，Web 直接调同一套 API。

### 落地顺序

```
1. 多租户隔离（Shop + shopId + Prisma 中间件）   ← 地基，不做后面全白搭
2. 权限点体系（Permission/Role，替换 adminOnly）  ← App 和 Web 共用
3. Web 端脚手架 + 登录 + 商品/库存表格
4. Web 端报表大屏 + 批量单据
5. AI 用量计费（按店计量，依赖 1）
```

## 优先级汇总

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0** | 修假必填（真校验） | 现在标了必填等于没标 |

| **P0** | 多租户隔离 | Web 上线前必须；不做就是数据事故 |
| **P1** | 可分组字段（groupable） | 商品多时的核心找货路径 |
| **P1** | 商品图片补齐 + 无图降级 | 开单选货最需要 |
| **P1** | 排序（默认"最近有动静"） | 开单效率 |
| **P1** | 权限点体系 | Web 端前置 |
| **P2** | 列表密度切换（列表/大图） | 服装类生意才强需求 |
| **P2** | 拼音首字母搜索 | 商品上千才明显 |
| **P2** | 字段拖拽排序 | 锦上添花 |
| **P3** | Web 端本体 | 上面都稳了再动 |
